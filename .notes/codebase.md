# Codebase Overview

This repository currently has two main parts:

- `backend/`: a Node + Fastify + Prisma API
- `frontend/`: a Vite-based frontend

The notes in this file explain the current backend structure and the reasoning behind it so the team has one shared reference point.

## Backend structure

The backend is organized by responsibility:

- `src/index.ts` is the entrypoint.
- `src/server.ts` starts the server and owns shutdown behavior.
- `src/app.ts` builds the Fastify app and registers plugins and routes.
- `src/config/env.ts` loads and validates environment variables once at startup.
- `src/lib/prisma.ts` creates the Prisma client and database pool in one place.
- `src/plugins/` is for reusable Fastify plugins.
- `src/routes/` is for top-level route registration.
- `src/modules/` is for feature-specific code grouped by domain.
- `prisma/schema.prisma` is the source of truth for database models.
- `src/generated/prisma/` is generated by Prisma and should not be edited by hand.

## Why this shape

This layout keeps the backend easy to reason about as it grows:

- Startup logic stays in one place instead of being mixed into routes.
- App composition stays separate from server booting, which makes testing and refactoring easier.
- Environment validation happens early so failures are obvious.
- Prisma lives behind a single shared module so we do not create duplicate clients or pools.
- Cross-cutting concerns like CORS stay in plugins instead of being scattered through handlers.
- Feature code can grow in `modules/` without turning `routes/` into a dumping ground.

## Working rules

When making backend changes:

1. Update the schema in `prisma/schema.prisma` first.
2. Run the appropriate Prisma command:
   - `npm run db:migrate` for real migrations
   - `npm run db:push` for quick local schema syncs
   - `npm run db:generate` after schema changes
3. Put feature code under `src/modules/<domain>/`.
4. Register routes from `src/routes/index.ts`.
5. Import Prisma from `src/lib/prisma.ts` instead of creating a new client in a handler.

## Decision note rule

For any future system or code decision, add a new note in `.notes/` with:

- the date
- the decision
- the reasoning
- any alternatives considered
- follow-up tasks

That keeps the repository history understandable without having to reconstruct context from code alone.
